==================================================
3. DIRECT-DOWNLOAD ARCHITECTURE NOW
==================================================

The site appears to block long-lived simultaneous viewer sessions with a
"multiple access" style popup.

Because of that, the current working model is:

1. User clicks `직접다운` on multiple lectures.
2. Jobs are queued in the background.
3. Only one hidden viewer tab is opened at a time to capture the actual playlist URL.
4. That hidden viewer tab auto-starts playback heuristically, captures the HLS `m3u8`,
   then closes quickly.
5. Once the playlist URL is captured, the actual download/remux work proceeds without
   needing that viewer tab to stay open.
6. This allows:
   - capture: sequential
   - actual media download/remux: parallel

This was designed to imitate the practical user experience they described with
FetchV: briefly open/capture, then continue downloading independently.

==================================================
4. WHY THIS DIRECTION WAS CHOSEN
==================================================

Earlier direct-download attempts failed because:

- page/content-script fetches hit CORS
- naive HLS merging naturally produced `.ts`, not `.mp4`

Those blockers were addressed with:

- viewer detection + background/service-worker downloading
- `mux.js` remux for TS-based HLS to MP4
- offscreen document + IndexedDB for file assembly
- service worker owning the final `chrome.downloads.download(...)` call

==================================================
6. IMPORTANT RECENT BUGFIX
==================================================

When two or more direct-download jobs were running in parallel, the monitor list
kept reordering itself on every progress update.

Cause:

- sorting used `updatedAt`
- whichever job reported progress most recently jumped above the other one

Fix:

- active jobs are now ordered by `createdAt`
- completed/failed jobs still sort by recency

Practical effect:

- active download cards no longer jump up/down and cause visual confusion

==================================================
7. CURRENT LIMITATIONS
==================================================

Still true:

- Chrome's native downloads panel does not show progress during the internal
  fetch/remux/assembly phase.
- The Chrome download item appears only after the final object URL is handed to
  `chrome.downloads.download(...)`.
- Therefore, in-progress visibility must come from the extension UI
  (course badge / popup / monitor tab), not from Chrome's own download shelf.

Other limits:

- encrypted HLS is still unsupported
- extension reload during active download causes active jobs to be marked failed
- there may still be corner cases where hidden viewer auto-play/capture needs tuning
